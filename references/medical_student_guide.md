# 给医学生与生信研究者的算力白话指南（为什么任务会崩、会卡、会挨骂？）

跑单细胞（Scanpy / Seurat）、空间转录组、基因组比对或深度学习时，电脑和服务器其实只有 **4 样核心资源**：**CPU（几个工人）**、**内存 RAM（实验台桌面有多大）**、**硬盘 Disk（仓库有多大）**、**GPU 显存（特种流水线）**。

绝大多数“把服务器搞死被师兄师姐骂”、“跑了一晚上第二天发现任务没了”的问题，都源于下面 **3 个最常见的误区**：

---

## 误区一：“服务器有 32 个核，我开 32 个进程岂不是快 32 倍？”（结果整机卡死，连 SSH 都断了）

### 真相 1：隐式多线程爆炸（$32 \times 32 = 1024$ 线程惨案）
在 Python（`numpy`、`scipy`、`scanpy`、`torch`）和 R（OpenBLAS）里，**哪怕你只写了一个单进程脚本，底层数学库也会默认偷偷开满机器所有的 CPU 核心（比如 32 个线程）**。
- 如果你再用 `multiprocessing`、`ProcessPoolExecutor` 或 `joblib(n_jobs=16)` 开了 16 个进程，每个进程又各自开 32 个底层数学线程，机器上瞬间就有 **$16 \times 32 = 512$ 个线程**在争抢 32 个物理核心！
- **后果**：CPU 把 90% 的时间都花在“线程排队切换”上，你的代码反而比单核还慢 10 倍，同时把服务器的 SSH 登录守护进程挤死，谁也连不上。
- **解决办法（铁律）**：只要开启多进程（`workers > 1`），**必须把每个进程内部的底层线程锁死在 1 或 2**：
  ```bash
  export OMP_NUM_THREADS=1
  export OPENBLAS_NUM_THREADS=1
  export MKL_NUM_THREADS=1
  export VECLIB_MAXIMUM_THREADS=1
  export NUMEXPR_NUM_THREADS=1
  ```

### 真相 2：40%–60% 空闲资源甜点法则
永远不要按机器的“总核数”开并发，而是先看**现在还空着几个核（Idle Cores）**，只取空闲核数的 **40%–60%**。
- 既不会单核傻跑干等几个小时，也给同机其他同学、系统服务和你自己的其他会话留出呼吸空间。

---

## 误区二：“我看 `.h5ad` / `.rds` 文件才 4 GB，服务器还有 60 GB 内存，开 10 个并行肯定够！”（结果半夜静默消失 / OOM Killed）

### 真相 1：硬盘上的文件大小 $\neq$ 内存里的大小（3–5 倍膨胀定律）
硬盘上的 `.h5ad`、`.rds`、`.bam` 或 `.parquet` 都是**高倍率压缩**过的。
- 读进内存变成 32 位/64 位浮点矩阵、或者做 `normalize` / `PCA` / `距离矩阵 (cdist)` / `最优传输 (OT)` 时，一个 **4 GB 的文件在内存里通常会膨胀到 12 GB – 20 GB**。
- 如果你开了 10 个子进程，每个子进程各自复制一份 15 GB 的矩阵，瞬间就需要 **150 GB 内存**！

### 真相 2：怎么看“真内存”还是“假缓存”？
Linux 和 Mac 会把最近读过的文件暂存在内存里加速（叫 **File Cache / 页缓存**）。
- **`Anon`（匿名内存 / 程序实占）**：这是 Python / R 变量真正吃掉的内存，**绝对不可回收**，一旦超过上限就会触发 OOM。
- **`File Cache`（文件缓存）**：这是操作系统借用空闲内存存的文件，当你的程序需要内存时，系统会**自动释放**它。
- **`Swap`（交换分区）**：内存满时的“急救缓冲垫”。如果一台 64 GB 内存的服务器只有 **2 GB Swap**（很多实验室工作站都是这样配的），只要你的程序实占内存刚超红线一秒钟，没有任何缓冲，Linux 内核的 **OOM Killer** 就会立刻一枪爆头（`Killed` / `Exit Code 137`），甚至连报错日志都来不及写！

---

## 误区三：“进程还在 `top` 里，怎么跑了 5 个小时一行输出都没有？”（假死 vs 单核瓶颈）

用 `python3 scripts/task_watch.py` 可以一眼分清你的任务到底是下面哪一种情况：

| 状态标签 | 看到的现象 | 真正原因与解决办法 |
| :--- | :--- | :--- |
| 🟢 **HEALTHY (Multi-Core)** | `CPU%` 在 `400%–1200%`（代表同时吃满 4–12 个核），内存稳定 | **正常高速运行中**，安心去喝咖啡。 |
| 🟡 **SINGLE-CORE BOTTLENECK** | 机器有 32 个核，但你的任务长期卡在 **`99%–102% CPU`** | **单核串行瓶颈**：你在用纯单核 C++ 算子（如 `ot.emd`、`linear_sum_assignment`）或 Python `for` 循环。改成 `ProcessPoolExecutor` 按样本/Fold 并行可提速 8–10 倍。 |
| 🟠 **THREAD THRASHING** | 派生了几十上百个子进程/线程，整机 Load 飙到 50+，但进度极慢 | **线程踩踏**：忘了设 `OMP_NUM_THREADS=1`，赶紧停掉用 `safe_run.sh -t 1` 重启。 |
| 🔴 **STALLED / HUNG (0% CPU)** | 进程 PID 还在，但连续几分钟 **`CPU% = 0%`**，显存也没动 | **假死/死锁**：常见于 PyTorch `DataLoader(num_workers>0)` 共享内存死锁、网络下载断流卡住、或代码里不小心停在 `input()` 等待输入。直接杀掉排查。 |
| 💀 **OOM KILLED (Exit 137)** | 进程突然没了，或者返回码 `137` / `cgroup oom_kill +1` | **内存爆了被系统强杀**：把并发数 `-w` 减半，或者用 `sc.read_h5ad('data.h5ad', backed='r')` 按需读取。 |
